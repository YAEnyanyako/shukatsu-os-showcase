# ケーススタディ：通知を、根拠のある次の行動へ

## 1. 課題

就活では、企業の通知、プラットフォームの案内、選考課題、予約確認が別々の場所に届く。同じ会社でも送信元が違い、メールの件名にある「締切」が本人の対応期限とは限らない。

このデモでは、情報の分類から行動の更新までを一つの小さなフローに絞った。対象は、自分の応募状況を確認して行動したい利用者。すべての具体例は架空であり、実在の応募者や企業の記録ではない。

## 2. 成功の定義

- 会社が明記された通知を、送信プラットフォームに関係なく会社単位で見られる。
- 次の行動から、判断に使った通知と日付の意味を辿れる。
- 招待、本人の意向、予約確定を混同しない。
- 同じ通知を再処理しても、行動や予定が増殖しない。
- 新しい確認が来たら、既存の状態と衝突判定が更新される。

これらは機能の受け入れ条件である。利用者の満足度や採用成果の改善は、別途検証が必要になる。

## 3. 重要な設計判断

### 会社分類とイベント分類を併用する

「会社」と「何の通知か」は別の軸にした。Kumo Labs の案内はプラットフォームから届いていても同社へ分類する。一方、複数社を掲載するまとめ記事には特定の一社を割り当てない。会社名がないスカウトは確認待ちにする。

### 日付の型を分ける

Mori Systems のサンプルには、開催日時とキャンセル期限がある。これを単一の締切欄へ押し込むと、既に予約した人へ再度申込を促す可能性がある。回答・提出期限、開催枠、キャンセル期限を別々に保持する。

### 予約確認を状態変更の根拠にする

Aster Works の招待では検討タスクを作る。予約確認を取り込んだら、同じイベントのタスクを準備へ切り替える。古い招待が後から読み込まれても、確定状態を戻さない。

### 意向と完了を分ける

「検討を進める」は本人の意思を示すが、予約完了ではない。「保存」は未確定の案内を現在の行動から外す。実際の予約を取り消す効果は持たせない。

### 確定済みデータから重複を再判定する

Kumo Labs の体験会は、最初は Aster Works の面談と重なる。新しい確認通知で面談が変更されたら、イベントを同じ予定として更新し、重複を再計算する。サンプルの予定件数は2件のまま保たれる。

### 会社の下に独立したプロジェクトを置く

本選考とインターンは、会社が同じでも期限・職種・面接が異なる。v2 は会社 ID・プロジェクト ID・イベント ID を分け、Aster Works の二つの ES 締切とテスト期限を別々に追跡する。会社共通の宣伝メールは、コースを推測して割り当てない。

### 調べた情報を準備につなぐ

企業研究は7観点、経験談は年度・コース・段階を持つ模擬出典として整理する。素材棚は出典を保ち、ES の版と面接の回答はプロジェクトに紐づく。第三者の体験を自分の実績へ変換せず、自分が説明すべき問いに変える設計である。

### Calendar の境界を見せる

接続ボタンはローカルの模擬同期を起動する。確認済みイベントだけが対象となり、改期は同じ ID を更新する。ICS 出力は実際に動くが、外部カレンダーへの認証と書込は実装していない。

## 4. 役割分担

この公開版は AI 支援による実装であり、コードの独力実装や実務上のプロダクト責任者経験を主張するものではない。展示する対象は、要件の整理、状態と証拠の設計、例外ケース、検証可能な受け入れ条件である。仕様、コード、テストはそれぞれリポジトリから確認できる。

将来実際の AI 抽出を接続する場合も、モデルの出力だけで確定状態を書き換えず、検証段階を通す構成を想定している。この接続は未実装である。

## 5. 検証と残る課題

現在の自動テストは、重複排除、日付の区別、会社未確認、後着情報、日程更新、入力の不変性などを検証する。[評価資料](evaluation.md)に範囲を記載した。

残る課題は、実メールからの抽出品質、利用者による操作理解、所要時間、年度をまたぐ募集の移行管理、交通時間や未知の終了時刻を含む日程調整である。これらを実装済みの成果とは表現しない。

次の検証では、正解を先に定義した評価用データと、同じ条件の比較手順を用いる。正答率だけでなく、重要なタスクの漏れ、誤った期限、人による確認の量を個別に測る。
