# Shukatsu OS — 通知の根拠から、次にやることを選ぶ

[公開デモ](https://yaenyanyako.github.io/shukatsu-os-showcase/) · [操作ガイド](https://yaenyanyako.github.io/shukatsu-os-showcase/#guide) · [更新記録](../CHANGELOG.md)

通知を会社・募集ごとに整理し、根拠を確認して次の行動を選ぶワークフローのデモです。企業、通知、書類、日付はすべて新しく作った架空例で、実際の個人情報や選考記録は含めません。

**私の役割：** 要件定義、情報設計、受け入れ確認、改善の優先順位付け。会社と募集を分ける構造、根拠から状態を更新する条件、確認した文書を優先するルールを決めています。コードはAIコーディングツールで生成しています。

## 解決したかった問題

同じ会社でも別の募集があり、通知に書かれた「受付」「招待」「予約確定」は異なる状態を示します。資料を保存するだけでは、どの募集に関係し、どの文書を使い、何がまだ終わっていないか判断しにくいと考えました。

目指した流れは「散らばった通知 → 根拠を確認 → 次の一手」です。

## 架空のAster Worksで見る変化

Aster Worksには、プロダクト企画の本選考とAIビジネスインターンの通知があります。
会社だけでまとめると、本選考の面談予約とインターンの回答フォーム受付を取り違えかねません。受付を、書類通過や面接への進行と解釈するのも誤りです。
デモでは募集を分け、本選考の面談は「予約確定」の通知を根拠に表示します。
インターンの受領を反映しても、完了になるのはそのESだけです。適性テストは未完了で、書類通過や面接予約も追加しません。

## 代表的な設計判断

| 判断 | 受け入れ条件 |
|---|---|
| 募集を分ける | 同じ会社の本選考とインターンで、通知、期限、ESと回答が混ざらない |
| 確認した版を優先する | 確認済みv2を先に表示し、後日の未確認v3を含む他の版は折り畳む。日付と状態を読める |
| 内容の確認と提出を分ける | 「本人確認版にする」は文書内容への確認であり、提出や受領の証拠として扱わない |
| 招待を予約と扱わない | 明示的な案内で練習を開いても予約は作らない。書類選考の一部であるAI面接は書類通過と区別する |
| 再処理で増やさない | 同じ通知IDはスキップ。受領は該当作業だけに反映し、日程変更は同じ予定を更新する |

企業研究、資料分類、面接準備、未完了の確認やCalendarの詳細は[機能一覧](features.ja.md)にまとめています。

## 実際に動く操作と、架空例の境界

編集、版保存・確認、過去版の表示、資料の分類、状態ルール、回答保存、未完了の更新、日誌保存、PDF・ICS生成は、このブラウザで実行されます。入力はローカル保存領域にとどまり、公開ファイルには入りません。

通知本文と抽出結果、企業情報、経験談、質問は手作業で作った架空例です。研究の「収集」は既知の架空資料IDを保存する模擬操作で、検索やスクレイピングをしません。助言は簡易ルールと固定文です。Calendarの「接続」は模擬同期で、実メール、採用サイト、AI API、外部カレンダー、応募・予約・送信、夜間の自動実行は接続していません。

公開例は私用記録を置き換えたものではありません。実際の選考企業、書類、メールや個人のプロフィールは含めません。

私用環境は日常の就活で使用しています。公開デモは架空データです。私用環境の集計値は[プロフィール](https://github.com/YAEnyanyako)に記載しています（本人1名、2026年9月27日集計）。件数は利用の規模を示すもので、処理精度や時間削減の測定値ではありません。

## 受け入れ条件の検証と次の評価

受け入れ条件を45の自動テストに落とし込み、通知ルール、募集分離、確認版の優先、旧状態の復元、面接の時機、受領による該当作業の更新、再処理、未完了の確認、明示的な返答とPDF・ICS構造を検証しました。v2.1の機能更新時には公開ファイル38件の静的チェックも行いました。今回追加した入口資料と架空スクリーンショットも公開用のチェック対象です。[検証範囲](evaluation.md)

自動テストだけでは、実ブラウザの見た目・アクセシビリティ、AI精度、時間削減や採用成果を評価できません。次の評価では、根拠確認や版選択に要する時間、誤った状態への変更、確認版の取り違えを、条件を固定して測る必要があります。効果が未測定の段階で成果の数字を作りません。
